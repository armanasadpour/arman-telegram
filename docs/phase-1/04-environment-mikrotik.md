# شرایط محیطی اعلام‌شده و اثر آن بر طراحی

| مورد | پاسخ کارفرما | نتیجه طراحی |
|---|---|---|
| محل IBSng و هاست cPanel | هر دو در یک محل، داخل ایران | اتصال **محلی/شبکه داخلی**؛ Relay برای IBSng لازم نیست |
| NAS | MikroTik | تنظیمات RADIUS و Accounting طبق بخش ۳ |
| PHP | هر نسخه ۸ به بالا در دسترس | **PHP 8.3** به‌عنوان هدف (حداقل پشتیبانی‌شده: 8.2) |

## ۱. اتصال به IBSng (به‌روزرسانی تصمیم شماره ۱)

- **اگر cPanel و IBSng روی یک ماشین هستند:** `host = 127.0.0.1`، پورت 1235. هیچ تغییری در `IBS_SERVER_IP` و فایروال لازم نیست و رمز از شبکه عبور نمی‌کند. **بهترین حالت.**
- **اگر روی دو ماشین در یک شبکه داخلی هستند:** `IBS_SERVER_IP` روی IP داخلی سرور IBSng تنظیم شود، پورت 1235 در فایروال فقط برای IP داخلی هاست cPanel باز شود و روی اینترنت بسته بماند.
- گزینه Relay (HTTPS+HMAC) از طرح حذف نمی‌شود اما **غیرفعال و اختیاری** می‌ماند؛ فقط اگر روزی سرورها جدا شوند به کار می‌آید.

## ۲. تلگرام (هاست داخل ایران)

`api.telegram.org` از داخل ایران در دسترس نیست. بنابراین:
- **ارسال به تلگرام:** فقط از طریق Relay (مانند Relay موجود در `vercel.json` همین مخزن). آدرس پایه Bot API در پنل قابل تنظیم خواهد بود.
- **دریافت پیام‌ها:** Webhook مستقیم از سرورهای تلگرام به هاست ایران قابل اتکا نیست. دو راه:
  1. **Polling با `getUpdates` از Cron** از طریق همان Relay (ساده؛ تأخیر به اندازه بازه Cron، معمولاً ۱ دقیقه؛ اجرای چرخه‌ای ~۵۰ ثانیه با long-poll می‌تواند تأخیر را به چند ثانیه برساند).
  2. Webhook به Relay خارجی که آپدیت‌ها را به هاست ایران Forward کند (پاسخ سریع‌تر، یک قطعه دیگر برای نگهداری).
  - پیشنهاد: **گزینه ۱** برای نسخه اول؛ معماری طوری است که گزینه ۲ بعداً بدون تغییر منطق ربات اضافه شود.
- **ریسک:** Relay روی Vercel توکن ربات را می‌بیند و ممکن است در آینده از ایران فیلتر شود. Relay باید متعلق به خودتان باشد و آدرس آن قابل تعویض.
- **درگاه‌های بانکی داخلی** (سداد، به‌پرداخت، SEP، زرین‌پال) برای هاست ایران مزیت دارند: IP ایران معمولاً شرط پذیرندگی است.
- **پایش USDT:** APIهای بلاک‌چین (TronGrid، RPCهای اتریوم/BSC) ممکن است از ایران مسدود باشند؛ در فاز ۷ همین Relay یا سرویس معادل بررسی می‌شود.

## ۳. MikroTik (یافته‌ها از `docs/README.mikrotik` و `core/ras/rases/mikrotik.py`)

| مورد | جزئیات | اهمیت برای سامانه |
|---|---|---|
| RADIUS | `/radius add address=<IBSng> secret=… service=ppp` (و `hotspot` در صورت استفاده) | احراز هویت اکانت‌های فروخته‌شده |
| **Interim-Update** | `/ppp aaa set use-radius=yes accounting=yes interim-update=60` (برای HotSpot: `radius-interim-update`) | **حیاتی برای فروش حجمی**: بدون آن، credit (حجم) فقط پس از قطع اتصال کم می‌شود و کاربر می‌تواند بیش از حجم بسته مصرف کند |
| مصرف بالای ۴ گیگ | کد MikroTik در IBSng `Acct-Input/Output-Gigawords` را لحاظ می‌کند | بسته‌های ۵۰ و ۱۰۰ گیگ درست حساب می‌شوند |
| قطع اتصال (`killUser`) | IBSng با **SSH** به میکروتیک وصل می‌شود و `/ppp active remove` یا `/ip hotspot active remove` اجرا می‌کند؛ نام کاربری و رمز SSH در ویژگی‌های RAS ثبت می‌شود | ابزار SSH قدیمی IBSng ممکن است با الگوریتم‌های جدید SSH در RouterOS 7 سازگار نباشد → **در فاز ۳ آزمایش می‌شود**؛ در صورت شکست، قطع اتصال با RADIUS (Session-Timeout) یا API میکروتیک مستقیماً از سامانه بررسی می‌شود (نیازمند تأیید شما) |
| SNMP | IBSng آمار ترافیک پورت‌ها را از SNMP میکروتیک می‌خواند | برای نمایش لحظه‌ای in/out آنلاین‌ها |
| اتصال همزمان | `multi_login` در IBSng؛ در PPP میکروتیک محدودیتی برای یک نام کاربری نیست، کنترل با IBSng است | |
| سرعت | امکان ارسال `Mikrotik-Rate-Limit` از طریق `radius_attrs` | اگر بسته‌های با سرعت متفاوت می‌خواهید، در فاز ۴ اضافه می‌شود |

**اطلاعات لازم از شما در فاز ۳:** نسخه RouterOS (6 یا 7)، نوع سرویس (PPTP / L2TP / SSTP / OVPN / PPPoE / HotSpot) و اینکه Interim-Update فعال است یا نه.
