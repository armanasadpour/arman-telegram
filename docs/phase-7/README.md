# فاز ۷ — درگاه‌های پرداخت

## اصل طراحی
هر پرداخت موفق **فقط کیف پول پرداخت‌کننده را شارژ می‌کند** (ردیف `topup` در دفتر کل، کلید یکتای `pay:{id}`).
خرید مشتری بعد از آن از همان کیف پول کسر می‌شود (مثل فروش همکار در فاز ۵). نتیجه:
- پرداخت تکراری/بازگشت دوباره از درگاه دو بار شارژ نمی‌کند.
- اگر ساخت اکانت شکست قطعی بخورد، پول در کیف پول مشتری می‌ماند (قابل استفاده برای خرید بعدی) — بدون نیاز به برگشت وجه بانکی.
- همه چیز در یک دفتر کل تغییرناپذیر قابل حسابرسی است.

## روش‌ها
| روش | جریان | تأیید |
|---|---|---|
| زرین‌پال (v4) | request ← StartPay ← بازگشت ← verify | خودکار، مقایسه مبلغ |
| سامان (SEP) | token ← OnlinePG ← بازگشت ← VerifyTransaction | خودکار، مقایسه مبلغ |
| به‌پرداخت ملت | bpPayRequest (SOAP) ← startpay ← بازگشت ← bpVerifyRequest + bpSettleRequest | خودکار |
| سداد (ملی) | PaymentRequest (SignData 3DES) ← Purchase ← بازگشت ← Advice/Verify | خودکار |
| کارت‌به‌کارت | نمایش کارت ← ثبت شماره پیگیری/۴ رقم آخر/تصویر رسید | دستی توسط مدیر (عملیات حساس) |
| USDT (TRC20/ERC20/BEP20) | نمایش آدرس و مبلغ تتر با نرخ تعیین‌شده مدیر ← ثبت هش تراکنش | خودکار از اکسپلورر (TronGrid / Etherscan v2)؛ در صورت عدم دسترسی ← بررسی دستی |

## پرداخت‌کنندگان
- همکار: «شارژ کیف پول» در پنل و ربات.
- مشتری ربات: «خرید اکانت» و «تمدید» در ربات — لینک پرداخت آنلاین، کارت‌به‌کارت یا تتر؛ پس از تأیید، اکانت ساخته/تمدید و مشخصات در ربات ارسال می‌شود.

## امنیت
- کلیدها و رمزهای درگاه رمزنگاری‌شده در تنظیمات؛ تغییر با تأیید مجدد رمز؛ در لاگ نمی‌آیند.
- تأیید فقط سرور‌به‌سرور؛ پارامترهای بازگشت فقط برای پیدا کردن تراکنش استفاده می‌شوند. مبلغ تأییدشده باید با مبلغ پرداخت برابر باشد.
- قفل ردیف پرداخت هنگام تأیید؛ هش تراکنش تتر و شماره مرجع بانکی یکتا (استفاده دوباره ممکن نیست).
- تراکنش تتر باید بعد از ایجاد درخواست پرداخت ثبت شده باشد و تأییدهای کافی داشته باشد.

## محدودیت
مستندات درگاه‌های ایرانی از محیط توسعه قابل دسترسی نیست؛ پیاده‌سازی بر اساس مستندات منتشرشده و شناخته‌شده هر درگاه است و با شبیه‌ساز تست می‌شود. **قبل از استفاده واقعی، با هر درگاه یک تراکنش آزمایشی واقعی (مبلغ کم) لازم است.** هر درگاه تا آن زمان «تأییدنشده» علامت می‌خورد.

## معیارهای پذیرش
- [x] پرداخت موفق دقیقاً یک بار شارژ می‌کند (بازگشت تکراری، رفرش، فراخوانی دوباره).
- [x] مبلغ نادرست/تراکنش ناموفق شارژ نمی‌کند؛ پرداخت ناموفق هیچ اثری ندارد.
- [x] کارت‌به‌کارت فقط با تأیید مدیر و با دلیل؛ رد کردن بی‌اثر.
- [x] تتر: هش تکراری، آدرس/قرارداد/شبکه اشتباه، مبلغ کم، تأیید ناکافی، تراکنش قدیمی ← رد.
- [x] خرید مشتری ربات پس از پرداخت انجام و مشخصات ارسال می‌شود؛ شکست ← پول در کیف پول مشتری.
- [x] تست‌های فازهای قبل سبز.

## نتیجه (نسخه 0.7.0)
- **تست‌ها:** ۱۸۰ تست روی SQLite و MariaDB سبز (۲۱ تست جدید پرداخت + تست محدودیت درخواست).
  - زرین‌پال: کامل، لغو، Authority جعلی، تأیید ناموفق، قطعی بانک ← تأیید دوباره با Cron و شارژ فقط یک بار.
  - سامان: فرم POST به درگاه، مغایرت مبلغ، شماره مرجع تکراری.
  - ملت: ترتیب bpPayRequest ← bpVerifyRequest ← bpSettleRequest؛ تأیید ناموفق بدون تسویه.
  - سداد: SignData با 3DES دقیقاً طبق فرمول.
  - کارت‌به‌کارت: رسید تصویری، تأیید فقط با دسترسی و تأیید مجدد رمز، تأیید تکراری بی‌اثر، رد.
  - تتر: TRC20/ERC20/BEP20 (۶ و ۱۸ رقم اعشار)، هش تکراری، گیرنده/توکن اشتباه، مبلغ کم، تراکنش ناموفق، تأیید ناکافی ← Cron، اکسپلورر قطع ← بررسی دستی.
  - ربات: خرید آنلاین/کارت/کیف پول، شکست ساخت ← پول در کیف پول مشتری، تمدید فقط اکانت متصل، شارژ کیف پول همکار.
- **تست واقعی روی Apache با شبیه‌ساز زرین‌پال:** تنظیم درگاه و کارت در پنل ← همکار ۵۰ هزار تومان آنلاین شارژ کرد (رفت به درگاه و برگشت) ← کارت‌به‌کارت با تصویر رسید ← تأیید مدیر ← موجودی درست. مشتری در ربات خرید کرد، لینک پرداخت را باز کرد، پرداخت کرد؛ اکانت ساخته و مشخصات در ربات ارسال شد و رمز از صف پیام‌ها پاک شد.

## اشکال‌هایی که در تست واقعی پیدا و رفع شد
1. **سیاست امنیتی مرورگر (CSP)** انتقال به درگاه را مسدود می‌کرد؛ اکنون صفحه پرداخت فقط آدرس همان درگاه را مجاز می‌کند.
2. **محدودیت تعداد درخواست** در Laravel بین همه صفحات مشترک بود (چند کلیک در یک صفحه، صفحه دیگری مثل ثبت کارت‌به‌کارت را مسدود می‌کرد). اکنون برای هر مسیر جداست — این اشکال از فازهای قبل بود.
3. تأیید دستی فقط پس از ثبت اطلاعات واریز توسط پرداخت‌کننده ممکن است.

## نسخه 0.7.1 (رفع اشکال گزارش‌شده و درخواست‌های کاربر)
- **توقف وارد کردن اکانت‌ها روی ردیف ۱۶۶٬۵۰۰:** MySQL هاست روی ساعت تهران است و ستون‌های TIMESTAMP زمان‌هایی را که در «ساعت جهش» تابستانی سال‌های قبل (مثل `2022-03-22 00:11:35`) می‌افتند رد می‌کند. همه ستون‌های TIMESTAMP به DATETIME تبدیل شدند (تبدیل با همان منطقه زمانی که داده با آن نوشته شده بود؛ هیچ مقداری جابه‌جا نمی‌شود — روی MariaDB با ساعت تهران از 0.7.0 به 0.7.1 آزمایش شد). این تبدیل بعد از هر به‌روزرسانی خودکار تکرار می‌شود. وارد کردن اکانت‌ها دیگر به‌خاطر یک ردیف نامعتبر متوقف نمی‌شود (شمارش «رد شده» + لاگ) و خطای خام پایگاه داده به کاربر نشان داده نمی‌شود.
- **حذف گروهی اکانت‌های منقضی** (صفحه اکانت‌ها ← «حذف منقضی‌های قدیمی»): پیش‌فرض بیش از ۶۰ روز (حداقل ۳۰)، پیش‌نمایش تعداد و فهرست، تأیید مجدد رمز + دلیل + تایپ تعداد، اجرای پس‌زمینه با Cron و دکمه «ادامه همین الان»/«توقف». پیش از حذف هر اکانت، اطلاعات زنده از سرور خوانده می‌شود: تمدیدشده یا آنلاین ← حذف نمی‌شود. هر حذف در گزارش رویدادها.
- **تاریخ شمسی همه‌جا:** تاریخ‌های سرور (اولین اتصال، ساخت) و مقادیر تاریخ در گزارش رویدادها هم شمسی شدند.
- **تقویم شمسی** برای فیلدهای تاریخ (بدون کتابخانه خارجی؛ تبدیل تاریخ با پیاده‌سازی PHP پنل در ۳۰۰۰ روز متوالی مطابقت داده شد).
- **تست‌ها:** ۱۸۵ تست روی SQLite و MariaDB (با ساعت تهران و جدول‌های منطقه زمانی) سبز.
